# Nhako Beam motion spec

Version 0.1, Phase 1. Values come from [`design/tokens/tokens.json`](../../design/tokens/tokens.json) under `motion`, `gesture` and `haptic`. Open [`design/tokens/preview.html`](../../design/tokens/preview.html) (served over http) to see and play every spring.

---

## 1. Rules that apply to everything

1. **Springs for movement, durations for fades.** Anything that changes position, size, scale or rotation uses a spring preset. Only opacity and color changes use the fixed durations.
2. **Always interruptible.** Every animation can be grabbed or reversed mid-flight. A new target starts from the current position and current velocity, never from the start. No "wait until the animation ends" states.
3. **Velocity carries over.** When a finger or cursor lets go, the release velocity becomes the spring's starting velocity. A hard flick flies further and faster than a slow release.
4. **1:1 tracking while dragging.** During a drag, the element sits exactly under the pointer (or follows with the `magnet` spring when the design says "lag"). It never animates toward the finger with a delay.
5. **Exits are quicker than entrances.** Entering uses a spring; leaving uses `fast` fade plus a short move. Users already know what is leaving.
6. **Only animate transform and opacity** (and Compose `graphicsLayer`). Never animate width, height, top or left in the real apps, so the GPU does the work and we hold 60fps (120fps on capable phones). Layout changes use FLIP (measure, then animate a transform).
7. **Nothing loops unless something is happening.** The radar sweep runs only while searching; the beam pulse runs only while bytes are moving. Idle screens are still.
8. **Bounce is earned.** `bouncy` is reserved for arrival and success: a device appears, a request is accepted, a transfer finishes. Everything else settles with no or tiny overshoot.

## 2. Spring presets

Mass is always 1. `dampingRatio` 1 means no overshoot.

| Preset | Ratio | Stiffness | Settles in | Overshoot | Use |
|---|---|---|---|---|---|
| `press` | 1.0 | 1800 | ~200 ms | 0% | Press and release on buttons, rows, chips |
| `snappy` | 0.9 | 900 | ~200 ms | 0% | Toggles, checkmarks, selection pill, badge swaps |
| `smooth` | 1.0 | 400 | ~430 ms | 0% | **Default.** Layout shifts, list reorder, sheets, cards |
| `gentle` | 1.0 | 180 | ~640 ms | 0% | Big surfaces, screen to screen transitions |
| `bouncy` | 0.6 | 500 | ~450 ms | 9.5% | Arrival and success moments only |
| `magnet` | 0.75 | 650 | ~310 ms | 2.8% | Dragged files pulled to a target; things that trail a finger |
| `settle` | 0.8 | 350 | ~430 ms | 1.5% | Snap back or fly out after a swipe is released |

Platform mapping (generated by `build.mjs`):
- **Desktop (Motion library):** `spring.smooth` gives `{ type: 'spring', stiffness: 400, damping: 40, mass: 1 }`.
- **Desktop (pure CSS):** `var(--spring-smooth)` with `var(--spring-smooth-duration)`. This is a `linear()` easing sampled from the real spring, with a `cubic-bezier` fallback for older WebKitGTK.
- **Android (Compose):** `NhakoMotion.smooth.spec<Float>()` gives `spring(dampingRatio = 1f, stiffness = 400f)`.

### Fixed durations (fades and color only)

`instant` 90 · `fast` 150 · `base` 220 · `slow` 320 · `slower` 480 ms. Easing: `standard` (0.2, 0, 0, 1) by default, `enter` (0, 0, 0, 1) for fade-ins, `exit` (0.3, 0, 1, 1) for fade-outs.

### Stagger

Lists and groups enter 30 ms apart, capped at 6 items (so the last one starts at most 180 ms late). Items beyond 6 enter together with the 6th.

## 3. Gesture physics

| Setting | Value | Meaning |
|---|---|---|
| Drag slop | 4px pointer, 8dp touch | Movement needed before a press becomes a drag |
| Swipe commit | 40% of card width **or** 650 dp/s | Either one commits the swipe |
| Fly-out speed | at least 1200 dp/s | A committed card leaves at least this fast, even after a slow drag |
| Max tilt | 6° | Card rotates with horizontal offset, pivot at the bottom center |
| Rubber band | coefficient 0.55 | Resistance past an edge |
| Magnet radius | 120 | Distance at which a dragged file stack starts leaning toward a device |
| Magnet snap | 44 | Distance at which it locks onto the device |
| Magnet pull | 0.35 | How strongly it leans (0 = none, 1 = jumps to target) |
| Long press | 420 ms | Opens context actions on Android rows and orbs |
| Sheet dismiss | 30% of height **or** 900 dp/s | Drag down distance or speed that closes a sheet |

**Rubber band formula** (Apple style). `x` is how far past the edge the finger is, `d` is the container size, `c` is the coefficient:

```
offset = (1 - 1 / ((x * c / d) + 1)) * d
```

The further you pull, the less it moves, and it can never pass `d`.

**Magnet formula.** With `dist` as the distance from the stack center to the device center, inside the magnet radius:

```
strength = magnetPull * (1 - dist / magnetRadius)
drawnPosition = pointer + (deviceCenter - pointer) * strength
```

Inside the snap radius, the stack jumps to the device center with the `magnet` spring and fires the `magnetSnap` haptic once. It releases (with `thresholdDeactivate`) when the pointer leaves the snap radius plus 12, so it does not flicker on the edge.

## 4. Choreography: the key moments

Each moment lists what moves, which preset, the haptic (Android), and the reduced-motion version.

### 4.1 App opens (home / radar)
1. Canvas fades in `fast`.
2. Your own orb scales from 0.94 to 1 with `smooth`, centered.
3. Search ring starts its 2.4s sweep (`linear`, looping) while discovery runs.
4. Known and nearby devices pop in around you with `bouncy`, staggered 30 ms, each from scale 0.6 and 40% opacity.
5. If nothing is found after 8s, the sweep slows to a gentle 1.6s pulse and the empty-state hint fades in.

Reduced motion: no sweep, no pop. Devices fade in `base`. A static "Looking for devices" label replaces the sweep.

### 4.2 A device appears or disappears while you watch
- Appears: pops in at its slot with `bouncy`; other orbs slide aside with `smooth` (FLIP).
- Disappears: fades to 0 over `fast` while scaling to 0.9; neighbors close the gap with `smooth`.
- No haptic (it is not your action).

### 4.3 Desktop: dragging files in from the file manager
1. Files enter the window: the canvas dims slightly (scrim at 30% over `fast`) and a file stack appears under the cursor (scale from 0.9 with `magnet`).
2. Device orbs lift to elevation 2 and show "Drop to send".
3. Near an orb (magnet radius): stack leans toward it; orb grows to 1.08 with `snappy`.
4. Inside snap radius: stack locks onto the orb with `magnet`; orb ring turns accent; label changes to "Send to Aisyah's laptop".
5. Drop on an orb: stack shrinks into the orb (scale 0.3, opacity 0, `smooth`), orb does one `bouncy` pulse, the transfer card slides up from the bottom with `smooth`.
6. Drop on empty space: a "Choose a device" sheet opens with the stack pinned at the top.
7. Drag leaves the window: everything reverses from its current position (interruptible).

Reduced motion: no lean or lock movement. The target orb gets an accent ring and label change only, and the dim is a plain fade.

### 4.4 Android: pick files then choose a device
1. Tap "Send files" (or arrive from the share sheet): picker opens (system).
2. Returning with files: the file stack drops in at the top with `bouncy`; radar orbs become tappable targets with a soft breathing ring.
3. Tap an orb: stack flies along a gentle arc into the orb with `smooth` (curved path, 300 to 450 ms depending on distance). No extra haptic on a plain tap; the system click is enough.
4. Long press and drag the stack onto an orb also works (same magnet rules as desktop, with `dragStart` and `magnetSnap` haptics).

### 4.5 Waiting for the other side to accept
- The sending orb shows a slow ring pulse (opacity 0.4 to 1, 1.6s, `standard`) and the text "Waiting for Aisyah to accept".
- A cancel button is always visible.
- If declined: the stack slides back out of the orb and fades with `settle`, card shows "Aisyah declined", `decline` haptic.
- After 60s with no answer: text changes to "Still waiting" with a "Cancel" and "Keep waiting" choice. Never auto-cancels silently.

### 4.6 Incoming request (the swipe card)
1. Card enters from the bottom with `bouncy` (from 24 down, scale 0.94), canvas dims to scrim.
2. **Drag:** card follows the finger 1:1 horizontally, tilts up to 6° around its bottom center, and gains opacity on the side you are heading: an "Accept" label (success) fades in on the left edge when swiping right; "Decline" (danger) on the right edge when swiping left. Vertical drag is rubber banded.
3. **Crossing the commit threshold** (40% or fast enough): label snaps to full opacity with `snappy`, card scales to 1.02, `thresholdActivate` haptic. Dragging back under it: reverses, `thresholdDeactivate` haptic.
4. **Release committed:** card flies off in the swipe direction with `settle`, starting from release velocity (minimum 1200 dp/s), `accept` or `decline` haptic. On accept, the transfer view rises behind it with `smooth`.
5. **Release not committed:** card springs home with `settle`, keeping release velocity, so a little flick overshoots naturally.
6. **Buttons:** tapping Accept or Decline plays the same fly-off as a committed swipe.
7. **Desktop:** the same card appears as a toast-style panel (top right of the window and as a system notification). Mouse drag works the same; keyboard: `Enter` accept, `Esc` decline.

Reduced motion: no tilt or fly-off. Card fades in, buttons are the main path, swiping still works but the card simply fades out on commit.

### 4.7 Pairing with a code
- **Sender, showing a code:** QR draws in (scale 0.94 to 1, `smooth`), words appear one by one with 60 ms stagger. A thin countdown ring around the QR drains over the code's lifetime (`linear`). In the last 20s the ring turns warning color.
- **Receiver, typing words:** each correct word locks in with a small `snappy` scale and check. A wrong word gets a gentle horizontal shake: 3 cycles, 6px, built from `snappy` (not a CSS keyframe wobble) plus a `decline` haptic.
- **Match found:** both screens show the two device orbs sliding toward each other with `smooth` and meeting with one `bouncy` pulse, `pairMatched` haptic. Then straight into the send or receive flow.
- **QR scan (Android):** camera view with a rounded viewfinder; when a code is recognized the viewfinder corners snap onto the QR's bounds with `magnet`, then the match animation plays.

### 4.8 Transfer in progress (the beam)
- **Fill:** the beam's fill width follows real progress via a `smooth` spring retargeted every update (about 10 times a second), so it never jumps or crawls unevenly.
- **Glow:** `beamGlow` shadow intensity tracks throughput: brighter when fast, dim when slow. Changes over `slow`.
- **Travel shimmer:** a soft highlight moves along the filled part, speed tied to current throughput (faster transfer, faster shimmer). Solid color highlight, no gradient. Stops instantly when paused.
- **Numbers:** percent, speed and time left use tabular numbers. Speed is smoothed (average over the last 3s) so it does not flicker. Time left only appears after 3s of data.
- **File list:** each file row shows its own small progress line; finished rows get a check with `snappy` and move to the bottom of the list with `smooth` (FLIP).
- **Connection badge** swaps with a `snappy` crossfade if the route changes (for example Relayed to Direct).

Reduced motion: no shimmer and no glow pulse. Fill updates in steps with a `fast` fade. Numbers keep updating.

### 4.9 Pause, resume, reconnect
- **Pause:** shimmer stops, beam fill desaturates to `textTertiary` over `base`, label "Paused". Button morphs from pause to play icon (`snappy` crossfade with a small rotation).
- **Resume:** reverse, and shimmer restarts from the current fill edge.
- **Connection lost:** beam keeps its fill, gets a slow breathing opacity (1.6s), warning banner slides down with `smooth`: "Reconnecting. Your progress is safe." No haptic unless it gives up.
- **Reconnected:** banner slides away, beam continues from the last confirmed chunk. If a few % were rolled back, the fill eases back with `smooth` (honest, not hidden).

### 4.10 Done
- Beam fill reaches 100%, glow fades out over `slow`.
- The beam collapses into a check mark inside the device orb: bar scales down horizontally toward the orb (`smooth`), check draws in (stroke animation, `base`), orb pulses once with `bouncy`. `transferDone` haptic.
- Actions fade in after 120ms: "Open", "Show in folder" (desktop) or "Open", "Share" (Android).
- The card auto-collapses into History after 6s, unless hovered or focused.

Reduced motion: check fades in, no collapse animation.

### 4.11 Failed or cancelled
- Beam fill stays where it stopped and turns `danger` over `base`.
- Card does one small horizontal shake (same as wrong word) and shows the reason plus a "Try again" action. `transferFailed` haptic.
- Cancelled by you: no shake, no haptic, card slides away with `settle`.

### 4.12 Screen transitions
- **Forward** (home to settings, home to history): new screen slides in 24 from the right and fades in with `gentle`; old screen fades to 0 and shifts 8 left.
- **Back:** reverse. On Android the predictive back gesture drives this transition with the finger (scale 0.9 preview, rubber banded), using the system API.
- **Sheets:** rise from the bottom with `smooth`, scrim fades `base`. Drag down to dismiss with velocity handoff.
- **Desktop panes** (expanded layout): content swaps with a `fast` crossfade plus 8 offset. No full-screen slides on desktop.

### 4.13 Micro interactions
| Element | Motion |
|---|---|
| Button press | Scale 0.97 with `press`, background to pressed color over `instant` |
| Hover (desktop) | Background overlay 4% over `fast`; cards lift to elevation 2 with `smooth` |
| Toggle | Thumb slides with `snappy`, track color over `fast`, `toggleOn`/`toggleOff` haptic |
| Segmented control | Selection pill slides between options with `snappy` |
| Checkbox / check | Stroke draws in over `base` |
| Copy code | Icon swaps to a check with `snappy`, toast "Copied" |
| Toast | Enters from 24 below with `smooth`, swipe sideways to dismiss with velocity |
| Tooltip | Fades in after 600 ms hover, `fast` |
| List reorder / insert | FLIP with `smooth`, new rows fade in from 0.94 |
| Pull to refresh (Android device list) | Rubber banded pull, radar ring spins with pull distance, release triggers a new scan |
| Focus ring | Appears instantly (no animation), so keyboard users are never kept waiting |

### 4.14 Launch intro (Phase 8)
Plays once on a fresh launch: from the launcher on Android, on every start of the desktop app. Not after a rotation, not when files are shared into the app (they go straight to the device picker), and never twice in one run.

- **Frame 0** is the system splash on Android (brand blue, the bolt from `splash_bolt.xml`) and the window's background color on desktop. The intro draws the same picture in the same place, so the hand-over doesn't move.
- **Press, 0 to 180 ms:** the bolt scales to 0.94 and its dark blue shadow tucks under it (`standard` easing).
- **Pop, from 180 ms:** the bolt springs back to 1 and the shadow slides out again on `bouncy`. A thin white ring (45% opacity) grows from 64 to 168 around the bolt and fades out over 520 ms (`enter` easing).
- **Hand-over, 580 to 820 ms:** the blue fades to 0 while the bolt shrinks to 0.82 (`exit` easing, 240 ms). The app underneath is already drawn and live.
- **Total about 820 ms**, inside Android's guidance of 1 second at most for splash animations. No haptic: a launch isn't a decision.
- Android holds touches until it's gone (under a second). On desktop it lets clicks and keys through.

Reduced motion: the blue fades out over 200 ms. Nothing moves.

## 5. Haptics map (Android)

Restraint is the rule: haptics confirm a decision or a physical threshold, never routine taps (system click sound and ripple already cover those).

| Event | Constant (API 34+) | Fallback |
|---|---|---|
| Start dragging a file stack | `DRAG_START` | `LONG_PRESS` |
| Swipe crosses commit threshold | `GESTURE_THRESHOLD_ACTIVATE` | `CLOCK_TICK` |
| Swipe goes back under threshold | `GESTURE_THRESHOLD_DEACTIVATE` | `CLOCK_TICK` |
| File stack locks onto a device | `SEGMENT_TICK` | `CLOCK_TICK` |
| Accept a request | `CONFIRM` (API 30) | `VIRTUAL_KEY` |
| Decline a request, wrong code word | `REJECT` (API 30) | `LONG_PRESS` |
| Transfer finished | `CONFIRM` (API 30) | `VIRTUAL_KEY` |
| Transfer failed | `REJECT` (API 30) | `LONG_PRESS` |
| Pairing matched | `CONFIRM` (API 30) | `VIRTUAL_KEY` |
| Toggle on / off | `TOGGLE_ON` / `TOGGLE_OFF` | `CLOCK_TICK` |
| Button press, progress updates | none | none |

API levels were checked against the official Android `HapticFeedbackConstants` reference. Use `NhakoHaptic.Accept.perform(view)` in code. It respects the user's system haptics setting automatically.

Desktop has no haptics. The visual parts of the same moments carry the feedback.

## 6. Reduced motion

Triggered by: Android "Remove animations" (animator duration scale 0), desktop `prefers-reduced-motion: reduce`, or the in-app setting **Motion: System / Full / Reduced** (`data-motion` attribute on desktop).

| Normal | Reduced |
|---|---|
| Position, scale, rotation springs | Opacity crossfade over `fast` |
| Radar sweep, beam shimmer, glow pulse | Off; static labels say what is happening |
| Swipe fly-off and tilt | Fade out on commit |
| Bouncy arrivals | Plain fade in |
| Shake on error | Color change plus icon, no movement |
| Stagger | Kept but halved (15 ms), since it is a fade |

Information is never carried by motion alone, so nothing is lost in reduced mode.

---

## 7. Performance budget

- 60fps minimum everywhere; 120fps on Android devices that support it. No frame over 16ms during any animation on a mid-range phone (target: a 2021 Snapdragon 7-series class device).
- Animations start within 1 frame of input (no waiting on the network or disk to animate).
- Progress updates from the Rust core are throttled to about 10 per second for UI. The spring smooths between them.
- Phase 2 verification: Playwright records each flow at 60fps and captures a performance trace. Any long task over 50ms during an animation is a bug.
